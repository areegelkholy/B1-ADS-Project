# Design documentation: TISA-16 assembler, simulator and debugger

#CSCE 2200 Applied Data Structures, Project B1, Milestone 2.

# 1. What the application does
The assembler (asm) translates TISA-16 assembly code written in a source file, such as program.asm, into 16-bit machine words. It generates two output files: program.hex, which contains the machine code, and program.lst, which contains the assembly listing along with a sorted symbol table.

The simulator (sim) then loads the machine words from program.hex into a simulated machine and executes them. It can also take an optional interrupts.txt file to handle scheduled interrupts. During execution, it displays the values produced by OUT instructions and provides a report when the program halts. Alternatively, the simulator can be launched in debugger mode using the -d option, which opens an interactive debugger prompt.

Both the assembler and simulator follow the TISA-16 reference sheet exactly. This ensures that the machine code generated by our assembler is compatible with any other team's simulator that follows the same instruction-set specification.

## 2. Architecture

The project is divided into two main layers: the data structure layer, located in the ds/ folder, and the application layer, located in the app/ folder.

The data structure layer is independent of the assembler and simulator. It contains reusable data structures and does not need to know anything about CPUs or assembly language. The application layer uses these data structures through their public functions to implement the actual project features.

Input and output operations, such as reading files, writing files, and displaying information on the console, are handled only in the two main files and in the debugger. This separation makes the assembler and simulator classes easier to test because their main logic is not directly dependent on file or console operations.

The architecture starts with two entry points: asm_main.cpp and sim_main.cpp. The first launches the assembler, while the second launches the simulator.

On the assembler side, the Tokenizer reads each assembly source line and separates it into labels, mnemonics, and operands. The Macro component handles macro definitions and replaces macro calls with their corresponding bodies before the first assembly pass. The Expression component evaluates constant expressions using the shunting-yard algorithm. The ISA component provides the instruction-set information, including opcodes, register names, bit manipulation helpers, and disassembly. These components support the Assembler, which performs the two assembly passes and generates the machine-code file and assembly listing.

On the simulator side, the Simulator maintains the machine state and handles instruction fetching, decoding, execution, prefetching, interrupts, and runtime errors. It uses DynamicArray for memory and registers, and Queues for prefetching and interrupt handling.

The Debugger provides an interactive command prompt and uses a HashSet to manage breakpoints. The Profiler identifies the most frequently executed instructions using a MinHeap. The Pipeline component simulates a five-stage instruction pipeline to calculate the required clock cycles and analyze data and control hazards. It uses five Queues, one for each pipeline stage, along with a DynamicArray for tracking information.

Overall, this architecture separates reusable data structures from application-specific functionality. Each component has a clear responsibility, and the data structures are selected according to the operations required by each component.

# How the components communicate with each other:
The communication between the components follows a clear sequence.

First, the assembler is launched. The asm_main file reads the assembly source file and stores its content as a string. It then passes that string to Assembler::assemble(text), which starts the assembly process.

Second, the assembler returns a result. The assemble() function returns either true or false, depending on whether the assembly was successful. If it succeeds, asm_main retrieves the generated machine code using hexText() and the assembly listing using listingText(), then writes them to their respective output files. If assembly fails, it prints the errors using errorText() and does not write the output files.

Third, the simulator is launched. The sim_main file reads the generated .hex file and passes its contents to Simulator::loadHexText(). It can also optionally load an interrupt file using loadInterruptText(). After loading the program, it either starts normal execution using run() or passes the simulator to a Debugger if debugger mode is selected.

Finally, the debugger and profiler interact with the simulator. They can read information from the simulator through functions such as getPc(), getMemoryWord(), and getExecCount(). They can also call step() to execute the next instruction. However, they never modify the machine state directly.

The main idea is that each component communicates through defined public functions. This keeps the components independent, makes the code easier to maintain and test, and prevents the debugger and profiler from directly interfering with the simulator's internal state.

## 3. Algorithms and how they use the data structures

### 3.1 Tokenizer
The Tokenizer is responsible for reading each line of assembly code and breaking it into smaller parts that the assembler can understand.

First, it removes comments. Anything written after a semicolon (;) is ignored.

Next, it checks whether the line contains a label. A label is the text that appears before a colon (:). Labels are case-sensitive, meaning that uppercase and lowercase letters are treated differently.

After that, the first word is identified as the instruction mnemonic. The mnemonic is converted to uppercase, which means instructions are case-insensitive. For example, add, ADD, and Add are treated as the same instruction.

Finally, the remaining text is split into operands using commas. Spaces inside operands are also removed because the specification says they should be ignored. For example, LEN - 1 becomes LEN-1.

The Tokenizer processes each character in the line once, so its time complexity is O(n), where n is the length of the line.

### 3.2 Expressions: shunting-yard (Stack + Queue)

The Expression component evaluates mathematical expressions used in assembly instructions. It uses the shunting-yard algorithm, together with a Stack and a Queue, to handle operator precedence and evaluate expressions correctly.
# Step 1: Tokenization

First, the expression is split into individual tokens, such as numbers, operators, parentheses, and symbols.

If a token is a symbol, the Expression component looks up its value in the symbol table using a HashMap. This lookup takes O(1) time on average.

It also identifies unary minus. For example, in -5, the minus sign represents a negative number rather than subtraction.

# Step 2: Shunting-yard algorithm
The algorithm converts the expression into postfix notation.
- Numbers are placed directly into the output Queue.
- Operators are temporarily stored in an operator Stack.
- Before pushing a new operator, operators with the same or higher precedence are moved from the Stack to the output Queue. This ensures the correct evaluation order.
- When an opening parenthesis ( appears, it is pushed onto the Stack.
- When a closing parenthesis ) appears, operators are moved to the output Queue until the matching opening parenthesis is found.
This ensures multiplication is performed before addition.

# Step 3: Evaluating the postfix expression

Once the expression has been converted, the algorithm evaluates the output Queue from front to back using a value Stack.
- If the token is a number, it is pushed onto the Stack.
- If the token is an operator, the required operands are popped from the Stack, the operation is performed, and the result is pushed back.
The implementation also handles errors such as division by zero, missing operands, and unbalanced parentheses. Division and modulo use truncation toward zero.

Time Complexity: O(m)

Each token is processed a constant number of times during conversion and evaluation. Therefore, for an expression containing m tokens, the overall time complexity is O(m).

### 3.3 Two-pass assembly

The assembler uses a two-pass approach to convert assembly code into machine code. This means it goes through the source code twice. Each pass has a different responsibility.

# Pass 1: Building the Symbol Table

During the first pass, the assembler goes through all the source lines while maintaining a location counter. The location counter represents the address of the next available memory location.

The main tasks in this pass are:
- Handling labels: When the assembler encounters a label, it stores the label's name and its current address in the symbol table, which is implemented using a HashMap.
- Checking duplicate symbols: If a label or .EQU constant uses a name that already exists, the assembler reports a duplicate-symbol error. Labels and constants share the same namespace.
- Handling directives:
  - .ORG changes the location counter to a specified address.
  - .EQU defines a constant and stores its value.
  - .WORD reserves memory for one or more words.
  - .SPACE reserves a specified number of words.
- Counting instructions: Every instruction, including pseudo-instructions, occupies exactly one word.
Expressions used in .ORG, .EQU, and .SPACE are evaluated during this pass. Therefore, they can only use symbols that have already been defined.

At the end of Pass 1, the assembler has collected all the label addresses in the symbol table. This is important because it allows the assembler to handle forward references, meaning an instruction can refer to a label that appears later in the source code.

When the assembler reaches JMP LOOP, the label LOOP has not been defined yet. During Pass 1, the assembler records its address when it eventually encounters the label. This allows Pass 2 to resolve the reference correctly.

# Pass 2: Generating Machine Code

During the second pass, the assembler goes through the source code again and converts each instruction into its corresponding 16-bit machine word.

It uses an opcode table, implemented using a HashMap, which maps each instruction mnemonic to its information:

OpInfo { opcode, format, extra }

This information tells the assembler which opcode to use and how to interpret the instruction's operands.

A switch statement based on the instruction format is then used to place the different fields into their correct positions within the 16-bit machine word.

Each field is shifted into its designated position and combined to produce the final instruction word.

The assembler also handles pseudo-instructions, such as MOV, INC, DEC, and CLR. These are rewritten into equivalent real instructions, such as ADD or ADDI, with adjusted operands. This means they can be encoded using the same instruction-encoding process and still occupy exactly one word.

Before generating the final machine code, the assembler validates the instructions by checking:
- Whether the register names are valid.
- Whether the correct number of operands is provided.
- Whether immediate values and addresses fit within their allowed ranges, such as imm6, imm9, 8-bit addresses, and 16-bit .WORD values.
- Whether the target address is within the valid memory range (not above 0xFF).
- Whether the memory address has already been used by another word.
Errors are collected instead of stopping at the first error. Afterward, they are sorted by source line number using heapSort, making the error messages easier to read.

Time Complexity: O(n)

Both passes visit each source line once. Since HashMap operations take O(1) time on average, the overall assembly process takes O(n) time, where n is the number of source lines.
Output Generation
After successful assembly, the assembler generates two outputs:

1. hexText() — Machine Code File

This function generates the hexadecimal machine-code output.

2. listingText() — Assembly Listing

This function generates a listing containing information about the assembled source code. Each source line includes its address, machine word, source line number, and original text.

For .WORD and .SPACE directives, multiple output lines may be generated because they can reserve multiple words.

At the end of the listing, the assembler prints the symbol table. It retrieves all symbol names using getAllKeys() from the HashMap, sorts them alphabetically using heapSort, and prints their corresponding values in hexadecimal.

### 3.4 The simulator cycle
The Simulator is responsible for executing the machine instructions. Its main function is Simulator::step(), which executes exactly one instruction cycle according to Section 6.1 of the TISA-16 specification.

Each time step() is called, the simulator follows these stages:

Step 1: Interrupt Check

Before executing the next instruction, the simulator checks whether there are any scheduled interrupts.

The interrupts loaded from the file are stored in a Queue and sorted by their scheduled cycle. When an interrupt's scheduled cycle is less than or equal to the number of instructions already executed, it is moved into another Queue called the pending-interrupt Queue.

If interrupts are pending and the Interrupt Enable flag (IE) is set to 1, the simulator handles the next pending interrupt.

It does this by:
1. Pushing the current Program Counter (PC) onto the simulated stack.
2. Pushing the current flags word onto the stack.
3. Setting IE = 0 to disable further interrupts.
4. Loading the interrupt handler address into the PC using PC = M[0xFC + n], where n is the interrupt number.
This allows the program to temporarily stop its normal execution and run the appropriate interrupt handler.

Step 2: Fetch

The simulator fetches the next instruction from the prefetch buffer using the current PC. The prefetch buffer is a Queue that temporarily stores upcoming instructions.

Step 3: Decode

After fetching the instruction, the simulator decodes its 16-bit machine word. It uses bit shifting and masking operations to extract the opcode, destination register, source registers, and other instruction fields.

The opcode tells the simulator which operation it needs to perform.

Step 4: Execute

The simulator executes the decoded instruction by updating the registers or memory as required.

Registers and memory are implemented using DynamicArrays.

Some important rules followed during execution include:
- Register R0 always reads as zero.
- Arithmetic results wrap around to 16 bits.
- Flags are updated according to Section 3 of the specification.
- The CMP instruction performs signed comparisons.
Step 5: Update Counters

After execution, the simulator increments the instruction counter and the execution counter associated with the instruction's memory address.

The instruction counter tracks the total number of executed instructions, while the per-address execution counter records how many times each memory address has been executed.

Time Complexity: O(1) per instruction cycle

Each instruction cycle performs a fixed number of operations, so one call to step() takes O(1) time.

If the program executes a HALT instruction, the simulator prints the execution report. If a runtime error occurs, it displays an error message containing the PC and the reason for the error, followed by a register dump.
The Simulated Stack
An important design decision is that the CPU stack is stored inside simulated memory rather than using our Stack data structure class.

The simulator uses the Stack Pointer (SP) to identify the current stack location. The stack is accessed through memory using M[SP].

For example, when the program executes a PUSH operation, the simulator updates the SP and stores the value in memory. When it executes POP, it retrieves the value from memory and updates the SP.

Programs can also access this stack through instructions such as LW and SW. The debugger displays the stack as part of the simulated memory.

Using a separate Stack object would be incorrect because the CPU stack is part of the machine's memory and must be accessible through normal memory instructions.

The pushWord() and popWord() functions also check the stack boundaries according to Section 6.2 of the specification. The stack limit is set to one address above the highest program word located below 0xFC.
The Prefetch Buffer (Queue)
The simulator also implements a prefetch buffer using a Queue with a maximum size of four entries.

Its purpose is to temporarily store the next four upcoming instructions before they are needed.

Each Queue entry contains two values:
- The instruction's memory address.
- The corresponding machine word.
When the simulator fetches an instruction, it removes the front entry from the Queue and then fills the available space with the next sequential instructions. It never fetches beyond address 0xFF.

When is the prefetch buffer flushed?

The buffer must be emptied whenever execution does not continue at the next sequential address (PC + 1).

This happens when:
- A branch is taken.
- A CALL instruction is executed.
- A RET instruction is executed.
- A RETI instruction is executed.
- An interrupt is entered.
- A SW instruction modifies a memory address that is already stored in the prefetch buffer.
For the last case, the simulator uses prefetchContains() to check whether the address being modified is among the four queued entries. If it is, the buffer is flushed so that the simulator does not execute an outdated instruction.

Why is flushing important?

Imagine that the prefetch buffer already contains instructions from addresses 10, 11, 12, and 13. If the program executes a SW instruction that changes the machine word at address 12, the copy of address 12 inside the prefetch buffer becomes outdated.

By flushing the buffer, the simulator ensures that the updated instruction is fetched from memory instead.

The project verified this behavior using random programs that overwrite their own code.





























### 3.5 Debugger (HashSet)
The Debugger allows us to control program execution, inspect the machine state, and manage breakpoints.

It uses a HashSet to store breakpoint addresses. A breakpoint is a memory address where we want the simulator to pause before executing the instruction.

The reason we use a HashSet is that it allows us to check whether an address is a breakpoint using:

breakpoints.contains(pc)

This operation takes O(1) time on average, which is important because the simulator checks for breakpoints before every instruction during normal execution.

How does breakpoint execution work?

When we use the run command, the debugger checks the current PC before executing each instruction.
- The first instruction is always executed, allowing the program to leave a breakpoint where it is currently stopped.
- After that, execution stops before an instruction whose address is stored in the breakpoint HashSet.
- The step [n] command executes the requested number of instructions without checking breakpoints.
How are breakpoints displayed?

The breaks command lists all the stored breakpoints. Instead of requiring a separate function to retrieve all HashSet elements, the debugger checks all 256 possible memory addresses using contains().

Because addresses are checked from the lowest to the highest, the output is automatically sorted.

The debugger also displays the next instruction in the following format:

AA: WWWW <disassembly>

This includes the memory address, the machine word, and its assembly representation.

Only real instructions are displayed. For example, the pseudo-instruction DEC R3 appears in its equivalent real instruction format:

ADDI R3, R3, -1

Time Complexity:
- Breakpoint lookup: O(1) average.
- Listing breakpoints: O(256), which is effectively constant because the memory address range is fixed.

### 3.6 Profiler (MinHeap), challenge
The Profiler identifies the K most frequently executed instructions in the program.

It uses a MinHeap that stores pairs of values:

(count, address)

Here:
- count represents how many times an instruction has been executed.
- address represents the memory address of that instruction.
The MinHeap is limited to a maximum of K entries.

How does the algorithm work?
1. The profiler examines the execution count of every memory address.
2. It inserts each address and its execution count into the MinHeap.
3. If the heap contains more than K entries, it removes the smallest entry.
4. It continues until all addresses have been processed.
Because the heap always removes the smallest entry when its size exceeds K, it eventually retains the K instructions with the highest execution counts.

Why use a MinHeap?

We use a MinHeap because we only need the K largest execution counts, not a complete sorting of all addresses.

The smallest element is always at the root, so removing it takes O(log K) time. This makes the approach efficient when K is much smaller than the total number of addresses.

If two instructions have the same execution count, the instruction with the lower memory address wins. This provides deterministic and consistent results.

Time Complexity: O(n log K)

For n memory addresses, each insertion or removal takes O(log K) time, while the heap stores at most K entries.

Space Complexity: O(K)

The heap never stores more than K entries.

### 3.7 Hash tables: double hashing, load factor 50%
In Milestone 1, the professor gave us feedback to use double hashing, maintain a 50% load factor, and avoid long linked lists.

To address this feedback, we implemented both the HashMap and HashSet using open addressing instead of separate chaining.

Open addressing means that all keys are stored directly inside one array of slots. Each slot can have one of three states:
- EMPTY: The slot has never been used.
- USED: The slot currently contains a key.
- DELETED: The key was removed, but the slot is marked as deleted rather than becoming empty.
How does Double Hashing work?

When two keys produce the same initial hash position, we need a way to find another available slot.

Instead of moving to the next slot sequentially, we use two different hash functions to calculate the probing sequence

The first hash function determines the initial position, while the second hash function determines how far we move when a collision occurs.

Because the two hash functions are different, keys that collide at the same initial position will usually follow different probing sequences. This helps reduce clustering.

Why must the table size be prime?

We use a prime number for the hash table size to ensure that the probing sequence can visit every slot.

Since the step size is between 1 and size - 1, and the table size is prime, their greatest common divisor is always 1

This guarantees that the probing sequence eventually visits every slot instead of getting stuck in a smaller repeating sequence.

Therefore, an insertion can find an available slot as long as the table is not full.

Maintaining a 50% Load Factor

The load factor measures how much of the hash table is occupied.
Our implementation maintains the load factor at no more than 50%.

During rehashing:
1. A new, larger table is created.
2. Its capacity is the next prime number greater than or equal to twice the previous capacity.
3. All existing keys are inserted again into the new table.
4. Deleted slots are removed because only active keys are reinserted.
Rehashing takes O(size) time, but it happens occasionally as the table grows. Therefore, insertion remains O(1) amortized, while lookup takes O(1) on average.

How does deletion work?

When a key is removed, its slot is marked as DELETED rather than EMPTY.

This is important because immediately marking a deleted slot as empty could break the search process.

For example, imagine two keys collided and the second key was placed after the first one. If we delete the first key and mark its slot as empty, searching for the second key might stop at that empty slot and incorrectly conclude that the key does not exist.

Instead, the search skips deleted slots and continues probing. When inserting a new key, the implementation can reuse a deleted slot. During rehashing, tombstones are eliminated.


### 3.8 Macro expansion (challenge: stack of active macro contexts)
The Macro component handles macro expansion before Pass 1 of the assembler. This means that the assembler's two passes never need to deal with macro definitions or macro calls directly. They only receive the expanded assembly instructions.

A macro is a reusable block of assembly instructions. Instead of writing the same instructions repeatedly, we define them once and call the macro whenever we need them.

he Macro component uses a HashMap and a Stack to collect and expand macros.

Step 1: Collecting Macro Definitions (HashMap)

First, the component goes through the source code and identifies all macro definitions, starting with .MACRO and ending with .ENDM.

Each macro is stored in a HashMap, where:
- The key is the macro name.
- The value contains the macro's parameters and its body instructions.
After storing the definition, the macro block is removed from the original program.

Macro names are case-insensitive, and a macro cannot have the same name as an existing instruction.

Using a HashMap allows the component to find macro definitions efficiently when it encounters a macro call.

Step 2: Expanding Macro Calls (Stack)

The component uses a Stack to manage active macro contexts.

Whenever it encounters a macro call, it creates a frame containing:
- The macro being called.
- The arguments passed to it.
- The position of the next instruction to expand inside its body.
- A unique number identifying that particular macro call.
This frame is pushed onto the Stack.

The expansion process always works with the frame at the top of the Stack. It takes the next instruction from the macro body and replaces the parameters with the corresponding arguments.

For example, if the macro has parameters x and y, and the call provides R1 and R2, every occurrence of x is replaced with R1, and every occurrence of y is replaced with R2.

If the expanded instruction contains another macro call, a new frame is pushed onto the Stack. This allows macros to call other macros, which is called nested macro expansion.

Once a macro body has been fully expanded, its frame is popped from the Stack, and the component continues processing the macro below it.

Step 3: Preventing Infinite Recursion

A macro might accidentally call itself, either directly or indirectly through another macro.
This creates an endless expansion process if there is no protection.

To prevent this, the Stack has a maximum depth of 16, defined by MAX_MACRO_DEPTH.
If the nesting depth exceeds this limit, the component reports an error. This prevents the program from entering an infinite expansion loop.

Step 4: Generating Unique Labels

Another important feature is the use of @@ inside macro bodies.

Every macro call receives a unique number. Whenever @@ appears in a macro body, it is replaced with that call's unique number.

This is necessary because calling the same macro multiple times could otherwise create duplicate labels. Unique labels ensure that each macro expansion has its own label names.

Step 5: Error Handling

The Macro component also checks for several possible errors, including:
- Incorrect number of arguments.
- Missing macro name.
- Invalid macro name or parameter.
- Duplicate macro definitions or parameters.
- Missing .ENDM.
- .ENDM appearing without a corresponding .MACRO.
- Nested macro definitions.
If an error occurs inside a macro body, the error is reported using the source line number of the macro call. This helps identify which macro invocation caused the problem.

Time Complexity: O(output size)

The expansion process takes O(output size) time because each macro body line is substituted once for every time it is expanded.

### 3.9 Five-stage pipeline (challenge: a queue per stage, data hazards)

The Pipeline component simulates how instructions would move through a five-stage CPU pipeline. Its main purpose is to calculate how many clock cycles a program would need to execute.

An important point is that the pipeline does not change the actual execution or results of the simulator. The Simulator already executes the instructions correctly. The Pipeline only analyzes their timing.

To do this, the Simulator records an execution trace containing the address and machine word of every executed instruction. Then, Pipeline::run replays this trace one clock cycle at a time.

Each instruction passes through these five stages:
1. IF (Instruction Fetch): Fetches the instruction from memory.
2. ID (Instruction Decode): Decodes the instruction and reads the required registers.
3. EX (Execute): Performs the arithmetic operation or calculates an address.
4. MEM (Memory Access): Accesses memory when required by the instruction.
5. WB (Write Back): Writes the result into the destination register.
Each stage has its own Queue, with a maximum capacity of one instruction.

During every clock cycle, instructions move from one stage to the next. The movement starts from the end of the pipeline, meaning WB moves first, followed by MEM, EX, ID, and IF. This prevents an instruction from moving into a stage before the previous instruction has left it.
1. Data Hazards (Read After Write)
A data hazard occurs when an instruction needs a register value that an older instruction has not written yet.

In our implementation, registers are read during ID and written during WB.
Without forwarding, the second instruction must wait in the ID stage until the first instruction writes its result in WB.

The number of waiting cycles depends on how close the dependent instructions are:
- An instruction immediately behind its producer waits 2 cycles.
- An instruction one position behind its producer waits 1 cycle.
During a stall, the instruction remains in ID, and EX receives an empty slot called a bubble.

One important detail is that an instruction in WB can write its register in the same cycle that another instruction in ID reads it.
2. Forwarding
Forwarding is an optimization that reduces data-hazard stalls.

Instead of waiting for the result to be written back to the register file, the result is passed directly from an earlier pipeline stage to the dependent instruction.
With forwarding, most data hazards can be resolved without waiting.

However, there is one important exception: the load-use hazard.
Even with forwarding, the loaded value is not available early enough for the next instruction's EX stage. Therefore, the ADD instruction must wait one cycle.

The same situation applies to POP instructions.
3. Control Hazards
A control hazard happens when the program changes its execution path.

For example, consider a taken branch or a JMP instruction.

The pipeline might already have fetched the next two sequential instructions before knowing that execution should jump somewhere else.

In our implementation, the branch, CALL, RET, RETI, or interrupt entry is recognized in the EX stage.

As a result, the next two fetched instructions are on the wrong execution path and must be discarded.

These two discarded instructions are represented as two bubbles in the fetch stage.

The implementation detects this using the execution trace: if the next executed instruction's address is not equal to the current address plus one, it identifies a control transfer.
4. Additional Rules
There are three important implementation details:
- R0 never causes a data hazard because it always contains zero.
- Hazards involving SP and the flags are ignored in this pipeline model.
- The pipeline uses simplified timing: one cycle per stage, with branches resolved in EX.
5. Pipeline Report and Performance
After replaying the execution trace, the Pipeline produces a report containing:
- Total number of instructions.
- Total number of clock cycles.
- CPI (Cycles Per Instruction).
- Data hazards: number of instructions that waited and total stall cycles.
- Control hazards: number of flushes and total bubble cycles.

6. Pipeline Log
This displays the pipeline stages for the first N clock cycles in a table.

It is particularly useful during the project demonstration because we can visually show instructions moving between stages, identify stalls, and observe bubbles caused by data and control hazards.


### 3.10 Complexity summary

| Operation | Cost |
|---|---|
| Symbol / opcode lookup | O(1) average |
| Assembling a program with n lines | O(n) |
| Evaluating an expression with m tokens | O(m) |
| One simulated instruction | O(1) (the buffer has only 4 entries) |
| Breakpoint check | O(1) average |
| Sorting k symbols / errors | O(k log k) |
| Top-K profiler | O(256 log K) |
| Macro expansion | O(size of the expanded program) |
| Pipeline replay | O(number of cycles) |

The main idea is that we selected each data structure based on the operations required by its component. For example, HashMaps and HashSets provide average constant-time lookups, Queues provide efficient FIFO operations, and Stacks manage LIFO operations. MinHeap allows us to find the top K instructions without sorting everything.

Overall, these choices help keep the project efficient and ensure that most operations have linear or constant-time complexity.

## 4. Design decisions and trade-offs
This section explains the important choices we made when designing the project, why we chose them, and what disadvantages or limitations come with each choice.

A design decision is a choice we make about how to implement something, while a trade-off is what we gain from that choice versus what we sacrifice.
1. Open Addressing, Double Hashing, and 50% Load Factor
We chose open addressing with double hashing for our HashMap and HashSet, following the professor's feedback.

Instead of storing elements in linked lists, we store them directly inside one contiguous array.

We use two hash functions:
- The first determines the initial position.
- The second determines the step size when a collision occurs.
We also maintain a maximum load factor of 50% to reduce collisions and improve lookup performance.

Why did we choose it?

It avoids long linked lists, reduces pointer operations, and provides efficient average lookup performance.

Trade-off: It requires extra memory because we keep the table relatively empty. It also requires tombstones to handle deletion correctly, and the table size must be prime.
2. Prime Table Sizes Using nextPrime
We use a function called nextPrime to find the next prime number when resizing the hash table.

Why did we choose it?

A prime table size ensures that the double-hashing probe sequence can visit every slot, provided the step size is relatively prime to the table size.

Trade-off: Finding the next prime requires additional computation, with O(√n) complexity. However, this only happens during rehashing, so it does not significantly affect normal lookups.
3. CPU Stack Stored in Simulated Memory
We decided to implement the CPU stack directly inside the simulator's memory rather than using our Stack class.

Why did we choose it?

The TISA-16 specification allows programs to access the stack through normal memory instructions such as LW and SW. Therefore, the stack must be part of the simulated machine's memory.

Trade-off: Our Stack class cannot be used for the CPU stack. Instead, it is used for other operations, such as expression evaluation.
4. Prefetch Buffer Implemented Using a Queue
We implemented the prefetch buffer using a Queue that stores pairs of instruction addresses and machine words.

Why did we choose it?

A Queue follows the FIFO principle: First In, First Out. This matches how upcoming instructions are fetched and consumed sequentially.

Trade-off: Operations such as contains() and getAt() on our linked-list Queue take O(n) time. However, the buffer can only contain four entries, so the overhead is negligible.
5. HeapSort for Symbols, Errors, and Interrupts
We chose HeapSort to sort symbols, errors, and interrupts.

Why did we choose it?

We already implemented a heap, so using HeapSort allowed us to reuse our existing data structure. It also guarantees O(n log n) sorting performance.

Trade-off: HeapSort is not stable, meaning equal elements might not maintain their original order. To solve this, we added an order field to errors and interrupts so that elements with equal sorting priorities can preserve their original file order.
6. Collecting Errors Before Sorting Them
Instead of stopping assembly when the first error occurs, we collect all errors and sort them by source line number.

Why did we choose it?

This allows the user to see multiple errors at once rather than repeatedly fixing one error and running the assembler again.

Trade-off: It requires additional code and memory to store the errors before displaying them.
7. Separating Input/Output from the Assembler and Simulator
We decided that the Assembler and Simulator classes should not directly open files or print information to the console.

Instead, file and console operations are handled by the two main files and the debugger.

Why did we choose it?

This makes the Assembler and Simulator easier to test because we can provide input strings and examine their returned results without depending on external files or console operations.

Trade-off: The main files need additional code to handle reading and writing files, but they remain relatively simple wrappers around the main classes.
8. Using std::string for Text
We chose to use the standard C++ std::string class for handling text.

Why did we choose it?

The professor allowed its use, and it makes text operations such as storing, modifying, and comparing strings easier.

Trade-off: We rely on a standard library class for text handling rather than implementing our own string container. However, all the core data structures required by the project are implemented by us.
9. Sorting the Interrupt File
Although the specification states that the interrupt file is already sorted, we decided to sort it when loading it.

Why did we choose it?

This makes the simulator more robust. If one interrupt appears in the wrong position in the file, it will not prevent later interrupts from being processed in the correct order.

Trade-off: Sorting introduces an additional O(k log k) operation during loading, where k is the number of interrupts.
10. Pipeline Replays a Trace Instead of Modifying the Simulator
We decided that the Pipeline should analyze an execution trace rather than directly control or modify the Simulator.

Why did we choose it?

The Simulator is already responsible for producing the correct program results. Separating pipeline timing from actual execution prevents pipeline logic from affecting the program's behavior or official instruction counts.

Trade-off: The Pipeline is only a timing model. It does not actually execute instructions on the wrong path, but instead represents incorrect fetches using bubbles.
11. Expanding Macros as Text Before Pass 1
We decided to expand all macros before the assembler begins its first pass.

Why did we choose it?

This keeps the existing two-pass assembler unchanged. Pass 1 and Pass 2 only process normal assembly instructions, without needing special logic for macros.

Trade-off: If an error occurs inside a macro body, its line number refers to the macro call rather than the original line inside the macro definition.
12. Not Supporting Unary Plus
We decided not to support unary plus in expressions because the specification only requires unary minus.

For example, -5 is supported, but +5 is not.

Why did we choose it?

We implemented the functionality required by the specification instead of adding unnecessary features.

Trade-off: Expressions beginning with unary plus, such as +5, produce a missing-operand error.



## 5. Data structure integration: summary

This section explains exactly where each data structure is used in our project and what role it plays. The purpose is to show that we did not implement data structures just for the sake of having them; each one supports a specific component and operation.
1. DynamicArray
Where is it used?
- In the Simulator for storing memory and registers.
- In the Assembler for storing source lines, the machine-code image, the assembly listing, and errors.
Why do we use it?

DynamicArray provides indexed storage that can grow when more elements are added. This makes it suitable for storing data that needs direct access through an index.

For example, the simulator can access a register using its index, such as registers[1] for R1.
2. Stack
Where is it used?
- In Expression.cpp for the operator Stack and value Stack.
- In Macro.cpp for managing active macro contexts.
Why do we use it?

A Stack follows the LIFO principle: Last In, First Out.

In expression evaluation, it temporarily stores operators and values while converting and evaluating expressions using the shunting-yard algorithm.

In macro expansion, it manages nested macro calls. The most recently called macro is expanded first, and once it finishes, the component returns to the previous macro.
3. Queue
Where is it used?
- In Expression.cpp for storing the postfix output.
- In Simulator for the prefetch buffer, incoming interrupts, and pending interrupts.
- In Pipeline.cpp, where each of the five pipeline stages has its own Queue.
Why do we use it?

A Queue follows the FIFO principle: First In, First Out.

This is useful when elements must be processed in the same order they were added.

For example, the prefetch buffer processes upcoming instructions sequentially, while interrupt Queues preserve the order in which interrupts should be handled.

In the Pipeline, each Queue represents a stage and temporarily holds the instruction currently occupying that stage.
4. HashMap
Where is it used?
- In the Assembler for the symbol table.
- In buildOpcodeTable for storing instruction information.
- In Macro.cpp for storing macro definitions.
Why do we use it?

A HashMap stores key-value pairs and provides O(1) average-time lookup.

For example, when the assembler encounters a label, it looks up its address in the symbol table. Similarly, the opcode table allows the assembler to retrieve the instruction's opcode and format using its mnemonic.

The macro table allows the Macro component to find a macro definition when it encounters a macro call.
5. HashSet
Where is it used?

- In the Debugger for storing breakpoint addresses.

Why do we use it?

A HashSet stores unique values and provides O(1) average-time membership checking.

Before executing an instruction, the debugger checks whether the current PC exists in the breakpoint set.

This makes the HashSet suitable because breakpoint checking happens repeatedly during program execution.
6. MinHeap
Where is it used?
- In the Profiler for identifying the K most executed instructions.
- In the implementation of heapSort.
Why do we use it?

A MinHeap keeps the smallest element at its root, allowing us to efficiently remove the smallest element.

The Profiler uses this property to maintain only the K largest execution counts. Whenever the heap exceeds K entries, the smallest entry is removed.

This avoids sorting every instruction just to find the top K.
7. HeapSort
Where is it used?
- In the Assembler for sorting errors and the symbol table.
- In Simulator::loadInterruptText() for sorting interrupts.
Why do we use it?

HeapSort provides O(n log n) sorting performance.

It ensures that errors are displayed in source-line order, symbols are displayed alphabetically, and interrupts are processed in their scheduled order.

We also measured the performance of our HashMap compared with a simple linear list when looking up every label once.

This explains why we chose a HashMap for the assembler's symbol table: it provides much better performance when working with large numbers of labels.

## 7. Limits
This section explains the current limitations of our project and identifies features that are not included in the implementation.

1. Macro Expansion Limitations

Our macro system uses plain text replacement. This means it supports defining macros, passing arguments, and expanding nested macro calls, but it does not support more advanced features such as:
- Conditional assembly.
- Default arguments.
We chose to implement the macro functionality required by the project without adding these extra features.

2. Pipeline Limitations

The pipeline is a timing model that replays the execution trace generated by the simulator.

It calculates clock cycles, stalls, and hazards, but it does not act as a second simulator or independently execute instructions.

Therefore, it analyzes performance rather than changing the actual program execution.

3. Simulator I/O Limitations

The simulator does not support general input/output operations. Its only output instruction is OUT, as specified by the TISA-16 instruction set.

4. Memory Directive Limitations

There are also restrictions on assembly directives:
- .SPACE is limited to reserving a maximum of 256 words.
- .WORD values must fit within 16 bits.
These restrictions ensure that the generated values remain within the supported memory and machine-word limits.

## 8. Assumptions where the spec is silent

This section explains the assumptions we made when the TISA-16 specification did not provide exact details about certain behaviors.

These assumptions help us make implementation decisions and ensure that all components behave consistently. They should also be confirmed with the TA.
1. Error Messages and Runtime Reports
We assume that all error messages and runtime reports should be printed to standard output rather than standard error.

We also assume that there should be exactly one space between the different parts of the message.
2. HEX File Contents
We assume that the .hex file must contain a line for every assembled word, including zero-valued words reserved by the .SPACE directive.

These zero words are considered occupied memory locations and are included when calculating the stack limit.
3. Assembly Listing Format
We assume that the .lst file should contain four columns:
1. Address, represented using 2 hexadecimal digits.
2. Machine word, represented using 4 hexadecimal digits.
3. Original source line number.
4. Original source text.
If a source line does not generate a machine word, the address and word columns are left blank.

For .WORD and .SPACE, the source text is displayed only on the first generated word.
4. Prefetch Flush Counting
We assume that a prefetch flush is counted whenever the buffer is emptied while it contains at least one instruction.

Since the buffer has a maximum capacity of four words and refills after every fetch, this means a flush is counted for:
- Every taken branch.
- CALL.
- RET.
- RETI.
- Interrupt entry.
- An SW instruction that modifies an address currently stored in the prefetch buffer.
5. PC Values After RET, RETI, and Interrupt Entry
We assume that RET, RETI, and interrupt entry use only the lowest 8 bits of the popped or vector word as the new Program Counter.

This ensures that the resulting PC is represented within the 8-bit address range.
6. PC Moving Beyond 0xFF
We assume that if the simulator executes the instruction at address 0xFF and execution continues sequentially without a branch, the simulator should stop with a runtime error.

7. Stack Overflow During Interrupt Entry
We assume that if the simulator cannot push the required information onto the stack while entering an interrupt because the stack is full, it should report a runtime error at the current PC.
8. Instruction Execution Limit
We assume that the simulator has a default instruction limit of 1,000,000 instructions.

The user can modify this limit using:
- -l N: Sets the instruction limit to N.
- -l 0: Removes the instruction limit.

9. Debugger Behavior
We made the following assumptions about debugger commands:
- run always executes the next instruction before checking for a breakpoint.
- step ignores breakpoints and executes the requested number of instructions.
- stack displays the stack contents from top to bottom

10. Instruction Counting During Runtime Errors
We assume that an instruction that causes a runtime error is not included in the instruction count.

However, a HALT instruction is counted because it executes successfully and terminates the program.
11. Exit Codes
We assume that the simulator and assembler use the following exit codes:
Exit code	Meaning
0	Successful execution ending with HALT.
1	Runtime error or instruction limit reached.
2	Usage errors or file-related problems.
